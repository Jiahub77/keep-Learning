## 1. 响应式流 Reactive Streams

**定义：** 响应式流是一种**异步数据流处理**的规范（标准），旨在处理异步序列中的元素，同时提供**非阻塞**的背压机制。

**核心目标：** 解决异步编程中数据生产者和消费者之间速度不匹配的问题。

### 1.1 四大接口（Java 9+ 已纳入 `java.util.concurrent.Flow`）

| 接口 | 作用 |
|------|------|
| `Publisher` | 数据发布者——生产数据并发送给订阅者 |
| `Subscriber` | 数据订阅者——接收并处理数据 |
| `Subscription` | 订阅关系——连接 Publisher 和 Subscriber，可控制数据请求量 |
| `Processor` | 既是 Publisher 又是 Subscriber——数据处理中间环节 |

### 1.2 处理流程

```
Publisher ──→ Processor ──→ Processor ──→ Subscriber
 (发布)       (转换)          (过滤)        (消费)
     ↑                                          │
     └──────────── request(n) ──────────────────┘
              （Subscriber 主动拉取，实现背压）
```

### 1.3 为什么需要这么一套规范

传统异步（回调、Future）的两个老毛病：

```java
// ① 回调地狱：异步套异步，代码横向长
orderService.getOrder(id, order ->
    userService.getUser(order.getUserId(), user ->
        payService.getPay(user.getId(), pay ->
            System.out.println(pay))));

// ② 没有流控：生产者拼命塞，消费者接不住
executor.submit(() -> {
    while (hasMore()) {
        queue.put(read());     // 无界队列，塞到 OOM
    }
});
```

响应式流把这两件事都规范掉了：**用声明式操作符串起来（解决 ①），用 `request(n)` 反向流控（解决 ②）**。

## 2. 背压 Backpressure

**定义：** 当数据**生产者的速度 > 消费者的处理速度**时，消费者通过**反向通知**机制告诉生产者"慢一点"或"我只要 n 个数据"，防止消费者被压垮。

**本质：** 背压是一种**流控机制**，让消费者**主动拉取（Pull）**而非被**被动推送（Push）**。

```
Publisher（每秒产生 1000 条数据）
        │
        ▼
Subscriber（每秒只能处理 100 条数据）

// 没有背压 → Subscriber 被淹没，OOM 或崩溃
// 有背压  → Subscriber 告诉 Publisher："我只要 100 条"，Publisher 按需发送
```

### 2.1 为什么必须有背压

因为异步模型下"生产"和"消费"在不同线程上运行，**生产者不会因为消费者慢而自动停下**。如果没有反向的流量控制信号，中间就只能靠无界队列缓冲——而无界队列的终点就是 `OutOfMemoryError`。

> **背压 = 把"无界缓冲"换成"有界 + 协商"。**

### 2.2 一个直观的类比

```
没有背压：水管直接往小水桶里灌     → 水漫出来（OOM）
有背压：  水桶满了就关阀门          → 灌满即停
丢弃策略：水桶满了就让水溢出去      → 丢数据，但不崩
```

## 3. request(n) 协议与规范约束

背压不是"建议"，而是响应式流规范里的**硬约束**。规范第 1 条就规定：

> **Rule 1.1**：`onNext` 的调用总次数，**不得超过** `request` 累计请求的数量。

```
Subscriber                          Publisher
    │                                  │
    │── onSubscribe(subscription) ────→│   订阅建立，但此时一条数据都不会发
    │                                  │
    │── subscription.request(2) ──────→│   只要 2 条
    │←──────────── onNext(a) ──────────│
    │←──────────── onNext(b) ──────────│   配额用完，生产者主动停下
    │                                  │
    │── subscription.request(1) ──────→│   再要 1 条
    │←──────────── onNext(c) ──────────│
    │                                  │
    │── subscription.cancel() ────────→│   取消订阅，生产终止
```

四个关键点：

1. **`onSubscribe` 先于一切**，`Subscription` 是背压的唯一通道；
2. **`request(n)` 是累加配额**，不是"速率限制"；
3. **`request(Long.MAX_VALUE)` 表示"无限制"**，等价于放弃背压（很多操作符内部就这么干）；
4. **`cancel()` 与 `request()` 必须线程安全**，可被并发调用。

## 4. Reactor 中的背压策略

Spring WebFlux 默认使用 **Project Reactor**。Reactor 提供 `Flux`（0..N 个元素）和 `Mono`（0..1 个元素），并内置多种背压应对策略。

### 4.1 依赖

```xml
<dependency>
    <groupId>io.projectreactor</groupId>
    <artifactId>reactor-core</artifactId>
    <version>3.6.11</version>
</dependency>
```

### 4.2 五种策略

| 策略 | 操作符 | 行为 | 适用场景 |
|------|--------|------|---------|
| **BUFFER**（默认） | `onBackpressureBuffer()` | 缓存到内存队列，等消费者慢慢取 | 生产速率短时突增、可容忍延迟；**队列必须有界，否则 OOM** |
| **DROP** | `onBackpressureDrop()` | 队列满时**丢弃新元素** | 允许丢数据的实时监控、日志采样 |
| **LATEST** | `onBackpressureLatest()` | 只保留**最新一个**，旧的全丢 | 实时报价、传感器最新值（只关心当前状态） |
| **ERROR** | `onBackpressureError()` | 溢出时抛 `OverflowException` | 不允许丢数据、要求快速失败 |
| **限速拉取** | `limitRate(n)` | 把下游的请求切成 `n` 一批，分批请求 | 控制预取量，避免一次拉太多 |

### 4.3 代码示例

```java
import reactor.core.publisher.Flux;
import reactor.core.publisher.FluxSink;
import java.time.Duration;

// ① limitRate：把"一次要 1000 条"拆成"每次 100 条"，降低内存峰值
Flux.range(1, 1000)
    .limitRate(100)                 // 实际按 75% 预取（首次请求 75 条，之后每 75 条补一批）
    .subscribe(i -> process(i));

// ② onBackpressureDrop：下游处理不过来就丢
Flux.interval(Duration.ofMillis(1))          // 每毫秒 1 条，很快
    .onBackpressureDrop(dropped -> System.out.println("丢弃：" + dropped))
    .subscribe(i -> slowProcess(i));         // 每条处理 10ms

// ③ onBackpressureLatest：只保留最新值（典型：股票行情推送）
Flux.interval(Duration.ofMillis(1))
    .onBackpressureLatest()
    .subscribe(price -> render(price));

// ④ onBackpressureBuffer：带容量上限 + 溢出回调
Flux.interval(Duration.ofMillis(1))
    .onBackpressureBuffer(1000,                       // 最多缓存 1000 条
                          dropped -> log("缓冲区满，丢弃：" + dropped))
    .subscribe(this::slowProcess);

// ⑤ Flux.create 时显式指定溢出策略
Flux.create(sink -> {
        while (hasMore()) {
            sink.next(read());
        }
        sink.complete();
    }, FluxSink.OverflowStrategy.DROP)       // BUFFER / DROP / LATEST / ERROR / IGNORE
    .subscribe(this::handle);
```

### 4.4 预取 prefetch 的取舍

很多操作符（`flatMap`、`concatMap`、`publishOn`）内部会**提前请求一小批数据**（默认 256），以减少"请求-响应"往返次数。

```
prefetch 越大 → 吞吐越高，但内存占用越大
prefetch 越小 → 内存越省，但请求次数多、吞吐下降
```

压测时可以显式调小：

```java
flux.flatMap(this::remoteCall, 16, 32)   // concurrency=16, prefetch=32
```

### 4.5 冷流与热流（理解背压的前提）

| 类型 | 特点 | 例子 |
|------|------|------|
| **冷流 Cold** | 每个订阅者都会触发一次完整的数据生产，各自独立 | `Flux.range()`、`Flux.fromIterable()`、HTTP 请求 |
| **热流 Hot** | 数据在订阅之前就已在产生，订阅者只能收到订阅之后的部分 | `Flux.interval()`、`Sinks.many()`、WebSocket 推送 |

背压主要对**冷流**有效——因为生产者可以"等你请求再发"。热流只能靠 DROP / LATEST / BUFFER 这类策略应对。

## 5. 背压的三种实现思路

抛开框架，背压的实现无非三条路：

| 思路 | 做法 | 代价 |
|------|------|------|
| **拉模式（Pull）** | 消费者主动 `request(n)`，生产者按需生产 | 生产者必须支持"暂停/恢复"，实现复杂 |
| **有界队列 + 丢弃策略** | 队列满时按策略 DROP / LATEST / ERROR | 会丢数据或失败，需业务确认可接受 |
| **限流 / 降速** | 信号量、令牌桶、`limitRate` | 只是削峰，不能根治生产消费速率失衡 |

## 6. HTTP 场景下背压的边界

响应式流在**进程内**的背压是完整的，但一旦跨到 **HTTP 协议**，背压就会"打折"：

```
浏览器/客户端  ←──HTTP──→  WebFlux 服务  ←──Reactive──→  数据库/下游服务
     │                          │                            │
     │   TCP 窗口/流控（隐式）    │       request(n)（显式）    │
     └──────────────────────────┴────────────────────────────┘
```

- **服务端 → 客户端方向**：HTTP/1.1 没有应用层背压语义，只能依赖 **TCP 滑动窗口 + Netty 的 channel writability** 间接限速。客户端读得慢，TCP 窗口收缩，Netty 写不出去，Reactor 的 `request(n)` 就会变小——**是"间接背压"，不是"显式背压"**。
- **客户端 → 服务端方向**（上传大文件）：WebFlux 读请求体是响应式的，下游处理慢，`request(n)` 变小，Netty 就停止从 socket 读——**这一侧背压是真实有效的**。
- **HTTP/2** 有流量控制窗口，比 HTTP/1.1 更接近真正的背压。

**结论：** WebFlux 的背压主要价值在**服务内部各环节之间**（Controller → Service → Repository → 网络客户端）以及**请求体读取**。指望它"让慢客户端不拖垮服务"是不现实的——那要靠限流、超时、熔断。
