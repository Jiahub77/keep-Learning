## 1. OCP 开闭原则

**定义：** 一个软件实体（类、模块、函数等）应该**对扩展开放，对修改关闭**。

在程序开发中，代码通常呈上下依赖的流程，例如：

```
Controller → Service → Dao
```

- **对扩展开放：** 当需要增加新功能时，应该通过新增代码来实现（如新增类、新增方法），而不是修改已有代码。
- **对修改关闭：** 避免修改已经测试通过、稳定运行的老代码，因为修改可能引入 bug，并且导致模块之间的耦合度升高。

**核心价值：** 降低因需求变更带来的风险，使系统更稳定、更易维护。

### 1.1 实现方式：抽象 + 多态

```java
// 抽象：定义"要做什么"
public interface UserDao {
    User findById(Long id);
}

// 实现 A：MySQL 版
public class UserDaoMysqlImpl implements UserDao {
    @Override
    public User findById(Long id) {
        // JDBC 查询
        return null;
    }
}

// 实现 B：新增需求时只加类，不动上面的代码
public class UserDaoOracleImpl implements UserDao {
    @Override
    public User findById(Long id) {
        // Oracle 查询
        return null;
    }
}
```

上层只依赖 `UserDao` 接口：

```java
public class UserService {
    private UserDao userDao;                      // 只认接口
    public void setUserDao(UserDao userDao) { this.userDao = userDao; }
}
```

### 1.2 XML 配置正是 OCP 的落地手段

这就是为什么 XML 配置和 OCP 关系这么紧——**换实现只需要改一行 XML，Java 代码一行不动**：

```xml
<!-- 原来用 MySQL -->
<bean id="userService" class="com.example.service.UserService">
    <property name="userDao" ref="userDaoMysql"/>
</bean>
<bean id="userDaoMysql" class="com.example.dao.UserDaoMysqlImpl"/>

<!-- 换成 Oracle：只改 ref 的值，UserService.java 完全没动 -->
<!-- <property name="userDao" ref="userDaoOracle"/> -->
<!-- <bean id="userDaoOracle" class="com.example.dao.UserDaoOracleImpl"/> -->
```

> 如果 `UserService` 里写的是 `new UserDaoMysqlImpl()`，那换数据库就得改 Java 代码、重新编译、重新测试——这就是"对修改开放"，违反 OCP。

## 2. 依赖倒置原则 DIP

**定义：**

- 高层模块不应该依赖低层模块，二者都应该依赖其**抽象**。
- 抽象不应该依赖细节，细节应该依赖抽象。

**核心思想：** 提倡**面向抽象编程、面向接口编程**，不要面向具体编程，让上层不再直接依赖下层，从而降低耦合度。

### 2.1 对比示例

```java
// ❌ 反面：面向具体编程，高层直接依赖低层
public class UserController {
    private UserService userService = new UserServiceImpl();   // 直接 new，耦合死
}
```

```java
// ✅ 正面：面向接口编程，依赖通过外部传入
public class UserController {
    private UserService userService;                  // 只声明"我需要一个 UserService"

    public void setUserService(UserService userService) {   // 从外面送进来
        this.userService = userService;
    }
}
```

配套 XML：

```xml
<bean id="userService" class="com.example.service.UserServiceImpl"/>

<bean id="userController" class="com.example.web.UserController">
    <property name="userService" ref="userService"/>
</bean>
```

### 2.2 "倒置"到底倒置了什么

```
传统依赖方向（高层直接依赖低层）：

   UserController ──依赖──▶ UserServiceImpl ──依赖──▶ UserDaoMysqlImpl
        （高层）              （中层）                （低层）
   改最底层，上面全要跟着改


依赖倒置后（都依赖抽象）：

   UserController ──▶ UserService（接口） ◀──实现── UserServiceImpl
        │                                              │
        └──────────▶ UserDao（接口） ◀──实现──────────────┘
                        ▲
                        └── UserDaoMysqlImpl / UserDaoOracleImpl

   箭头方向反转了：实现类反过来"指向"接口，而不是接口指向实现类
```

## 3. 两个原则合起来看：为什么需要容器

到这一步，问题出现了：

- 按 OCP，`UserService` 只依赖 `UserDao` 接口 ✅
- 按 DIP，依赖要从外部传进来 ✅
- **但"从外面传进来"这件事，谁来干？**

```java
// 如果还是自己干，等于绕了一圈又回到原点
public class UserService {
    private UserDao userDao;

    public UserService() {
        // 这里还是得 new 一个具体实现——又依赖具体类了
        this.userDao = new UserDaoMysqlImpl();
    }
}
```

要么在 `UserService` 里 new（回到耦合），要么在 `main` 里 new 完再 set（那 `main` 就变成了"对象装配中心"，几千个对象谁受得了）。

**把这个"new 对象 + 塞依赖"的活儿交给一个第三方——就是 IoC 容器。** 于是：

| 原则 | 解决什么 | 落到 Spring 上 |
|------|---------|---------------|
| OCP | 改功能不改老代码 | 换实现只改 XML 的 `ref` |
| DIP | 依赖抽象不依赖具体 | 类里只写接口 + setter，实现由容器给 |
| **IoC** | 谁来 new、谁来塞 | 容器负责 |
| **DI** | 怎么塞进去 | `<property>` / `<constructor-arg>` |
