# 完整实战与复习清单

## 1. 工程说明

[hello-maven](examples/hello-maven) 是一个完整的单模块 Java 21 工程，包含可执行主类、2 个 JUnit 测试和固定版本的构建插件。生产代码没有第三方依赖，测试依赖只用于测试。

```text
examples/hello-maven/
├── .gitignore
├── pom.xml
└── src/
    ├── main/java/com/example/learning/App.java
    └── test/java/com/example/learning/AppTest.java
```

示例中的价格以整数“分”计算；只演示构建、测试和打包，不是完整商品或支付系统。

## 2. 检查环境并进入工程

```bash
java -version
javac -version
mvn -v
cd /Users/mac/disk2/www/keep-learning/Maven/examples/hello-maven
```

最后一条是本仓库当前的绝对路径；换机器后进入对应工程目录。应能看到 `pom.xml`。首次构建通常需要网络下载插件和依赖。

## 3. 理解 POM

打开 [pom.xml](examples/hello-maven/pom.xml)，找到：

- GAV：`com.example.learning:hello-maven:1.0.0-SNAPSHOT`。
- packaging 省略，因此使用默认 `jar`。
- `maven.compiler.release=21`，字符编码 UTF-8。
- JUnit 使用 `test` scope。
- Compiler Plugin 编译，Surefire 运行测试，Jar Plugin 写入入口类。
- Clean、Resources、Install、Deploy 插件版本也被显式固定。

插件中的版本号用于保证示例配置明确；正式项目仍需按兼容性、安全更新和团队策略维护。

## 4. 执行测试

```bash
mvn test
```

预期：编译主源码和测试源码，执行 AppTest 的 2 个测试，失败和错误数量均为 0，最终 `BUILD SUCCESS`。

测试报告位于 `target/surefire-reports/`。如果显示 0 个测试，不算完成测试验证，应按排错文档检查。

选择单个测试方法：

```bash
mvn '-Dtest=AppTest#addsMoney' test
```

预期只执行加法测试。方法名和大小写必须与源码一致。

## 5. 打包与运行

```bash
mvn clean verify
java -jar target/hello-maven-1.0.0-SNAPSHOT.jar
```

预期输出：

```text
Hello, Maven!
Total cents: 12900
```

构建会执行单元测试，然后生成带 Main-Class 的普通 JAR。它没有把 JUnit 打进生产 JAR，也没有自动执行集成测试，因为示例没有配置集成测试。

```bash
jar tf target/hello-maven-1.0.0-SNAPSHOT.jar
```

应能看到主类 `com/example/learning/App.class`，不应看到 AppTest 或 JUnit 的类文件。

## 6. 安装到本地仓库

```bash
mvn install
```

默认本地仓库下预期出现：

```text
~/.m2/repository/com/example/learning/hello-maven/1.0.0-SNAPSHOT/
```

里面有项目 POM、JAR 及相关元数据。自定义了 localRepository 时以实际路径为准。

此操作方便同一机器的其他 Maven 工程按坐标依赖它，不会向远程仓库发布，也不会创建系统命令。这个示例没有配置发布仓库，不要把 `mvn deploy` 当作必须练习的一步。

## 7. 观察依赖与最终配置

```bash
mvn dependency:tree
mvn help:effective-pom
mvn help:evaluate -Dexpression=project.artifactId -q -DforceStdout
```

预期依赖树包含 JUnit 及其测试传递依赖，最后一条输出 `hello-maven`。先观察 dependencyManagement、scope 和插件配置，再尝试解释为什么这些依赖出现。

## 8. 动手练习

1. 将一个测试期望值改错，执行 `mvn test`，观察构建失败和报告，再恢复正确值。
2. 执行 `mvn package -DskipTests`，观察测试编译与执行的区别；之后恢复执行 `mvn clean verify`。
3. 将版本改成 `1.0.1-SNAPSHOT`，打包后观察 JAR 文件名与安装路径变化。
4. 将 JUnit 改为通过 BOM 管理，再比较依赖树是否保持预期。
5. 按第 7、10 篇搭建父子模块，先继承属性，再统一依赖和插件版本。
6. 构造两条不同版本的依赖路径，使用第 10 篇的方法解释并统一版本。

每次只改一个变量；通过测试和产物检查后再进行下一项，避免把多个问题叠在一起。

## 9. 复习问题

| 问题 | 核心答案 |
|---|---|
| Maven 是否替代 JDK？ | 否，Maven 负责组织构建，编译仍需要 JDK |
| GAV 是什么？ | groupId、artifactId、version |
| 执行 package 会不会 test？ | 会经过 test 阶段，已绑定任务是否执行还受跳过等配置影响 |
| package 会不会 clean？ | 不会，属于不同生命周期 |
| install 是否上传远程？ | 不会，项目构件安装到本地仓库 |
| dependencyManagement 会引入依赖吗？ | 不会，需要 dependencies 实际声明 |
| BOM 是否等于父 POM？ | 否，导入 BOM 主要复用依赖管理 |
| Maven 冲突时选择最高版本吗？ | 通常不是，需结合路径距离、管理配置和声明顺序 |
| 普通 JAR 包含所有依赖吗？ | 默认不包含 |
| test scope 的库进入生产运行 classpath 吗？ | 默认不会 |
| 聚合意味着继承吗？ | 不意味着，分别看 modules 和 parent |
| BUILD SUCCESS 证明业务正确吗？ | 不能，还要确认测试、门禁、产物和运行行为 |
