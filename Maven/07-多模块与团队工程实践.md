# 多模块与团队工程实践

## 1. 为什么拆模块

当项目包含可复用模型、业务服务、应用入口等部分时，可以使用模块明确职责和依赖边界。模块不是越多越好；一个简单应用用一个模块也合理。

```text
learning-parent/
├── pom.xml
├── learning-model/
│   └── pom.xml
├── learning-service/
│   └── pom.xml
└── learning-app/
    └── pom.xml
```

依赖方向示意：`learning-app -> learning-service -> learning-model`。禁止循环依赖，例如 service 依赖 app，而 app 又依赖 service。

## 2. 聚合与继承

聚合通过 modules 把项目组织在一起构建；继承通过 parent 复用项目配置。二者独立，实际工程经常让根 POM 同时扮演两个角色。

父/聚合 POM 的核心结构：

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0">
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.example.learning</groupId>
    <artifactId>learning-parent</artifactId>
    <version>1.0.0-SNAPSHOT</version>
    <packaging>pom</packaging>
    <modules>
        <module>learning-model</module>
        <module>learning-service</module>
        <module>learning-app</module>
    </modules>
</project>
```

modules 中是模块目录路径，不是 artifactId。上面的根 POM 需要配套真实子模块才能构建。

service 子模块示意：

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0">
    <modelVersion>4.0.0</modelVersion>
    <parent>
        <groupId>com.example.learning</groupId>
        <artifactId>learning-parent</artifactId>
        <version>1.0.0-SNAPSHOT</version>
    </parent>
    <artifactId>learning-service</artifactId>
    <dependencies>
        <dependency>
            <groupId>com.example.learning</groupId>
            <artifactId>learning-model</artifactId>
            <version>${project.version}</version>
        </dependency>
    </dependencies>
</project>
```

这里统一版本，所以可使用 `${project.version}` 表示同版本兄弟模块；独立版本模块不能盲目套用。大型工程通常由父 POM 的 dependencyManagement 管理模块版本。

## 3. Reactor 构建顺序

Reactor 收集模块、按实际依赖等关系排序，并依次或并行构建。modules 的顺序不是唯一依据；仅写 dependencyManagement 也不会建立实际模块依赖。

在根工程执行 `mvn verify`，参与同次构建的上游模块通常可以提供所需输出，不必每个模块先手动 install。若离开根工程单独构建子模块，上游构件则可能需要已安装或可从仓库获取。

```bash
mvn clean verify
mvn -pl learning-service -am verify
mvn -pl learning-model -amd verify
mvn -rf :learning-service verify
```

| 参数 | 含义 |
|---|---|
| `-pl` | 选择指定项目，可用模块路径或 `:artifactId` 等形式 |
| `-am` | 同时构建所选模块所需的上游项目 |
| `-amd` | 同时构建依赖所选模块的下游项目 |
| `-rf` | 从指定模块恢复 Reactor 构建 |
| `-fae` | 尽量继续可构建的模块，最后报告失败 |

`-rf` 不自动补齐已经跳过的上游输出。上次只运行到 package、当前又是新进程时，恢复可能因缺少本地安装的上游依赖失败；可改用 `-pl ... -am verify` 重新构建所需模块。

## 4. 私服与发布

私服通常分为：公共仓库代理、内部 release 托管仓库、内部 snapshot 托管仓库，以及供客户端下载的聚合入口。

POM 中的发布配置示意：

```xml
<distributionManagement>
    <repository>
        <id>internal-releases</id>
        <url>https://repo.example.com/repository/maven-releases/</url>
    </repository>
    <snapshotRepository>
        <id>internal-snapshots</id>
        <url>https://repo.example.com/repository/maven-snapshots/</url>
    </snapshotRepository>
</distributionManagement>
```

地址是占位示例。settings.xml 的 servers 使用相应 ID 提供上传认证。发布 SNAPSHOT 或 release 时，Maven 根据项目版本和配置选择目标。

`mvn deploy` 会上传产物，是发布动作；学习时无需执行。发布前应确认坐标、版本、目标仓库、测试结果和权限。向 Maven Central 发布还需要满足当前的命名空间、签名、元数据和发布平台要求，不是随便填一个上传 URL 即可。

## 5. CI 基本流程

一般的验证任务：

1. 检出源码。
2. 安装或选择约定 JDK。
3. 恢复合适的 Maven 缓存。
4. 通过秘密系统提供需要的 settings.xml 和凭据。
5. 使用已提交的 Wrapper 执行 `./mvnw -B -ntp clean verify`。
6. 保存测试报告和构建产物；失败时让任务失败。

如果项目尚未使用 Wrapper，则使用受控安装的 `mvn -B -ntp clean verify`。不要在没有 mvnw 的项目里直接套用 Wrapper 命令。

发布任务应单独控制权限和触发条件。构建工具返回成功还应结合测试数量、质量门禁和预期产物检查，避免“没有执行测试”的假成功。

## 6. 可重复构建与缓存

- 固定 JDK、Maven、依赖和插件版本，使用 Wrapper/工具链和受控镜像。
- Release 构件保持不可变，减少 SNAPSHOT、版本范围和动态版本。
- 提交 POM、Wrapper、必要项目配置；忽略 target、个人 settings 和凭据。
- 使用支持可重复归档的插件配置，例如受控的 `project.build.outputTimestamp`，并验证连续构建产物的差异。
- 缓存只是加速手段，不是构建正确性的前提；定期用干净或隔离本地仓库验证。
- CI 不应意外复用某开发者曾经 install 的未发布内部版本。

相同源码不必然产生字节完全相同的 JAR：时间戳、生成代码、环境变量、文件顺序和工具版本都可能影响结果。

## 7. 工具链与安全

Maven Toolchains 可协助让编译和测试插件使用指定 JDK，而 Maven 自身在另一个 JDK 上运行。需要工具链配置及相应插件支持，不是只写 release 就会自动下载 JDK。

依赖和插件都是供应链的一部分，插件还会在构建机上执行代码。只使用可信仓库和已审查版本，按团队流程扫描漏洞、许可证和秘密信息。Maven 3.8.1 起默认阻止某些外部 HTTP 仓库访问；优先升级仓库为 HTTPS，不要把关闭安全校验作为常规解决方案。

继承合并、依赖版本冲突和运行时排查详见 [继承与冲突处理详解](10-继承与冲突处理详解.md)。
