# 生命周期与项目构建过程

## 1. 生命周期、阶段、插件、目标

| 概念 | 含义 | 示例 |
|---|---|---|
| Lifecycle | 一组有顺序的阶段 | default、clean、site |
| Phase | 生命周期中的一个位置 | compile、test、package |
| Plugin | 提供具体构建能力的组件 | maven-compiler-plugin |
| Goal | 插件中可执行的任务 | compiler:compile |

阶段是流程位置，插件目标才执行具体工作。一个阶段可绑定多个目标，也可以没有目标；绑定关系取决于 packaging 和项目配置。

## 2. 三套内置生命周期

### 2.1 clean

```text
pre-clean -> clean -> post-clean
```

常规项目中 `clean` 会调用 Clean Plugin 清理构建输出，通常就是 `target/`。它不会默认清空 `~/.m2/repository`。

### 2.2 default

完整阶段顺序如下：

```text
validate
initialize
generate-sources
process-sources
generate-resources
process-resources
compile
process-classes
generate-test-sources
process-test-sources
generate-test-resources
process-test-resources
test-compile
process-test-classes
test
prepare-package
package
pre-integration-test
integration-test
post-integration-test
verify
install
deploy
```

常用阶段：

| 阶段 | 作用或约定 | 普通 jar 项目的常见目标 |
|---|---|---|
| validate | 检查项目满足构建条件 | 不一定有默认任务 |
| process-resources | 复制/过滤生产资源 | resources:resources |
| compile | 编译生产源码 | compiler:compile |
| process-test-resources | 处理测试资源 | resources:testResources |
| test-compile | 编译测试源码 | compiler:testCompile |
| test | 运行单元测试 | surefire:test |
| package | 创建项目归档 | jar:jar |
| integration-test | 执行集成测试的位置 | 需要配置相应插件 |
| verify | 检查测试结果及质量规则 | 取决于配置 |
| install | 把产物和 POM 安装到本地仓库 | install:install |
| deploy | 向远程发布仓库上传产物 | deploy:deploy |

`validate` 不会自动执行你想象的所有检查，`verify` 也不会自动产生覆盖率门禁。需要显式配置 Enforcer、JaCoCo 等工具。

### 2.3 site

```text
pre-site -> site -> post-site -> site-deploy
```

用于生成和发布项目站点。`site-deploy` 是发布站点，与 default 生命周期的 `deploy` 发布构件不同。

## 3. 调用一个阶段，执行同一生命周期的前序阶段

```bash
mvn compile
mvn test
mvn package
mvn verify
mvn install
```

`mvn package` 会走到 package，因此包含资源处理、编译、测试编译和单元测试等已绑定工作。它不会自动执行后面的 verify、install、deploy。

`mvn install` 包含 package 和 verify 等前序阶段；`mvn deploy` 包含 install 等前序阶段。后者会产生远程发布行为，必须先配置并确认目标仓库。

三套生命周期独立，`mvn package` 不会自动先 clean；`mvn clean verify` 表示先执行 clean 生命周期到 clean，再执行 default 生命周期到 verify。

不要惯性写 `mvn compile test package install`：这会重复请求重叠的阶段，可能重复执行任务。通常写 `mvn clean install` 即可。

## 4. 从源码到 JAR 的一次构建

以本目录 hello-maven 为例：

```text
pom.xml + 父模型/设置
        |
        v
计算有效模型、解析插件与依赖
        |
        v
src/main/resources -> target/classes
src/main/java      -> target/classes/*.class
        |
        v
src/test/resources -> target/test-classes
src/test/java      -> target/test-classes/*.class
        |
        v
Surefire 运行测试 -> target/surefire-reports
        |
        v
Jar Plugin 打包 -> target/hello-maven-1.0.0-SNAPSHOT.jar
        |
        v
verify 检查 -> 可选 install 到本地 -> 可选 deploy 到远程
```

Maven 通常会复用未变化的输出，具体增量行为由插件决定。怀疑残留文件影响结果时执行 clean，但不必每次开发构建都清理所有输出。

## 5. 单元测试与集成测试

- Surefire 通常绑定 test；默认识别 `Test*`、`*Test`、`*Tests`、`*TestCase` 等测试类名。
- Failsafe 常用于集成测试，默认识别 `IT*`、`*IT`、`*ITCase`，需要显式配置执行。
- 测试是否运行还取决于目录、框架引擎、插件版本、includes/excludes 和跳过参数。

Failsafe 插件配置示例，放入 `build/plugins`：

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-failsafe-plugin</artifactId>
    <version>3.5.2</version>
    <executions>
        <execution>
            <goals>
                <goal>integration-test</goal>
                <goal>verify</goal>
            </goals>
        </execution>
    </executions>
</plugin>
```

这些目标有默认阶段。实际项目还需要测试框架依赖、集成测试类，以及必要的服务启动/清理配置。Failsafe 在 integration-test 执行测试、在 verify 判断结果，让 post-integration-test 有机会清理环境。

因此通常调用 `mvn verify`，不要只停在 `mvn integration-test`；否则可能漏掉清理和结果检查。测试环境清理还应考虑异常中断，CI 可提供额外兜底。

## 6. 阶段调用与直接目标调用

```bash
mvn compile
mvn compiler:compile
mvn surefire:test
```

第一条执行生命周期到 compile。第二条只直接请求编译目标，不自动补齐前面的资源处理。第三条不会自动先编译主源码和测试源码，干净目录中可能出现没有测试可执行等问题。

日常构建优先使用阶段；分析依赖等独立任务则适合直接调用目标：

```bash
mvn dependency:tree
mvn help:effective-pom
```

## 7. 跳过测试的含义

```bash
mvn package -DskipTests
mvn package -Dmaven.test.skip=true
```

在标准 Compiler/Surefire/Failsafe 配置下：

- `skipTests`：通常仍编译测试源码，但跳过测试执行。
- `maven.test.skip=true`：通常同时跳过测试编译和执行。

自定义插件或其他语言测试工具可能有独立开关，应检查有效配置。跳过测试会降低验证范围，不应成为发布流程默认选项。

## 8. package、install、deploy 的边界

| 命令 | 项目 target 产物 | 本地仓库项目构件 | 远程仓库项目构件 |
|---|---|---|---|
| `mvn package` | 生成 | 不安装当前项目 | 不发布当前项目 |
| `mvn install` | 生成 | 安装 | 不发布当前项目 |
| `mvn deploy` | 生成 | 安装 | 发布 |

构建过程中这三个命令都可能下载插件和依赖。`install` 不是把程序安装成操作系统应用，`deploy` 也不等于自动把服务部署到服务器并启动。
