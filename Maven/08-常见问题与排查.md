# 常见问题与排查

## 1. 通用排查顺序

1. 保存完整命令和错误日志，从失败模块及第一个有意义的原因开始看。
2. `mvn -v` 检查实际 Maven/JDK，而不是只看 IDE 显示。
3. 确认当前目录、POM、settings、Profile 和分支。
4. 用 `mvn -e verify` 获取异常信息，必要时再用 `-X`。
5. 分别检查有效模型、依赖树、网络、测试报告和最终产物。
6. 修复原因后复跑原始构建，避免只证明某个孤立目标成功。

不要一遇到失败就删整个本地仓库，这可能掩盖问题，并丢失仅在本地 install 的构件。

## 2. 找不到 mvn 或 Java

| 现象 | 常见原因 | 检查方向 |
|---|---|---|
| `mvn: command not found` | 未安装或 PATH 无 Maven bin | 安装路径、重开终端 |
| JAVA_HOME 不正确 | 指向 bin、旧路径或已卸载 JDK | 指向真实 JDK 根目录 |
| macOS 找不到 Java Runtime | 只有系统占位命令 | 安装 JDK 并重新检查 |
| `invalid target release: 21` / `release version 21 not supported` | 编译器 JDK 太旧 | mvn -v、工具链、Compiler Plugin |
| `UnsupportedClassVersionError` | 运行时比生成字节码所需版本旧 | 运行 JDK、依赖字节码版本 |

即使主源码以 release 17 编译，某个依赖如果需要 Java 21，也不能在 Java 17 运行时使用。

## 3. Could not resolve dependencies / 找不到构件

依次检查：

- GAV、type、classifier 是否正确，版本是否真实存在。
- 构件是公开库还是公司内部库，仓库是否配置正确。
- SNAPSHOT 仓库是否允许 snapshots，release 仓库是否允许 releases。
- 私服认证、代理、DNS、网络和 HTTPS 证书。
- 本地是否存在失败下载记录，更新策略是否尚未允许重试。

```bash
mvn -U verify
mvn help:effective-settings
```

日志中的 `401` 常与认证有关，`403` 常与权限或仓库策略有关，`404` 常是路径/坐标不存在，也可能是仓库隐藏未授权资源。`PKIX path building failed` 应检查证书链及 Maven 所用 JDK 的信任库。

不要通过全局禁用 TLS 校验解决证书问题；公司代理证书应由可信流程正确部署。

若确认单个版本缓存损坏，先保留需要的本地产物，再只处理该构件对应目录并重试。不要随意删除整个 `~/.m2`，其中还可能有 settings、工具链和秘密信息。

## 4. “失败已缓存”与 .lastUpdated

下载失败后，Maven 可能留下 `.lastUpdated` 等状态记录，在更新策略允许前不再次请求。先修复网络、认证或坐标，再用 `-U` 重试；必要时只清理确认损坏的目标版本缓存。

如果构件只存在于某位开发者本地仓库，其他机器仍会失败。正确做法是通过 Reactor 一起构建，或把合法内部构件发布到受控仓库。

## 5. 测试没运行 / 没有发现测试

检查：

1. 文件是否在 `src/test/java`，类名是否匹配插件的默认规则。
2. 是否引入对应测试 API 和引擎，Surefire/Failsafe 是否支持当前测试框架。
3. 是否被 skip 参数、Profile、includes/excludes 排除。
4. 是否误用了 `mvn surefire:test`，而没有先编译测试。
5. 查看 `target/surefire-reports` 和日志中的测试数量。

```bash
mvn -Dtest=AppTest test
```

本目录示例预期执行 2 个测试。`BUILD SUCCESS` 本身不能证明测试被发现。

## 6. 编译通过，运行时报错

| 异常 | 可能原因 |
|---|---|
| `ClassNotFoundException` | 运行时加载不到目标类，检查 classpath 和产物 |
| `NoClassDefFoundError` | 可能缺少依赖，也可能类初始化曾经失败，需追踪最初原因 |
| `NoSuchMethodError` | 编译和运行时加载了不同的库版本 |
| `AbstractMethodError` | 接口/实现的二进制版本不匹配 |
| `ServiceConfigurationError` | SPI 文件或实现类缺失、冲突、版本不兼容 |

先看 [继承与冲突处理](10-继承与冲突处理详解.md)，再对照运行 classpath、容器提供的库和打包结果。依赖树只描述 Maven 解析结果，不能证明运行容器实际加载了哪个 JAR。

## 7. JAR 不能直接运行

- `no main manifest attribute`：没有配置 `Main-Class`，或它不是可执行应用 JAR。
- `Could not find or load main class`：入口类名或路径错误，或该类不在产物中。
- 主类找到但第三方类缺失：普通 JAR 默认不包含依赖，需要正确 classpath，或选择合适的可执行打包方式。

检查实际归档：

```bash
jar tf target/hello-maven-1.0.0-SNAPSHOT.jar
```

示例没有生产第三方依赖，已配置 Main-Class，所以可以用 `java -jar`。有依赖的应用不能直接照搬这个假设。

## 8. IDE 能跑，终端不能跑，或反过来

对比：Maven 版本、Maven runner JDK、项目 JDK、settings 路径、本地仓库、激活 Profile、环境变量、工作目录、测试运行器。

IDE 可能将所有模块直接加入运行 classpath，也可能使用自己的编译器。重新导入 Maven 项目后，以团队标准的命令行构建验证。不要只通过手动往 IDE Libraries 里添加 JAR 来修复 Maven 工程。

## 9. 修改配置后看似没生效

```bash
mvn help:active-profiles
mvn help:effective-pom
mvn help:evaluate -Dexpression=maven.compiler.release -q -DforceStdout
```

检查是否修改了正确 POM，属性是否被覆盖，execution ID 是否引发合并，父 POM 是否还是旧版。资源过滤结果要查看 target 中生成的文件。若是 Maven JVM 启动参数，修改配置后应启动新进程。

## 10. 远程发布失败

检查 `distributionManagement`、server ID 匹配、上传权限、版本策略、签名/元数据规则和产物是否已发布。Release 通常不允许覆盖；不要为了“让命令通过”覆盖已被其他项目使用的版本，应修正后发布新版本。

不要把带凭据的 settings、调试日志和私有仓库完整配置直接贴到公开平台。
