# 继承与冲突处理详解

本篇重点解决两个问题：父项目的配置如何进入子项目，以及最终使用的版本或配置为什么与你预期不同。

## 1. 继承、聚合、BOM 对比

| 机制 | 配置入口 | 作用 | 是否让其他模块参与同次构建 |
|---|---|---|---|
| 继承 | 子项目的 parent | 复用父 POM 的属性、管理和构建配置 | 不会自动聚合兄弟模块 |
| 聚合 | 根项目的 modules | 把多个项目纳入 Reactor | 会 |
| 导入 BOM | dependencyManagement 中 type=pom、scope=import | 复用依赖管理 | 不会 |

一个 POM 只能有一个直接 parent，但可以有多级父链，也可以导入多个 BOM。聚合工程不一定是子模块的父工程；父工程也不一定列出所有继承它的项目。

## 2. 可复用的父子配置示例

下面是两个完整 POM 的教学模板，需要创建对应目录后才能构建，并不属于附带的 hello-maven 单模块工程。

父目录 `learning-parent/pom.xml`：

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0">
    <modelVersion>4.0.0</modelVersion>
    <groupId>com.example.learning</groupId>
    <artifactId>learning-parent</artifactId>
    <version>1.0.0-SNAPSHOT</version>
    <packaging>pom</packaging>

    <modules>
        <module>learning-service</module>
    </modules>

    <properties>
        <maven.compiler.release>21</maven.compiler.release>
        <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
        <junit.version>5.11.4</junit.version>
    </properties>

    <dependencyManagement>
        <dependencies>
            <dependency>
                <groupId>org.junit</groupId>
                <artifactId>junit-bom</artifactId>
                <version>${junit.version}</version>
                <type>pom</type>
                <scope>import</scope>
            </dependency>
        </dependencies>
    </dependencyManagement>

    <build>
        <pluginManagement>
            <plugins>
                <plugin>
                    <groupId>org.apache.maven.plugins</groupId>
                    <artifactId>maven-compiler-plugin</artifactId>
                    <version>3.13.0</version>
                </plugin>
                <plugin>
                    <groupId>org.apache.maven.plugins</groupId>
                    <artifactId>maven-surefire-plugin</artifactId>
                    <version>3.5.2</version>
                </plugin>
            </plugins>
        </pluginManagement>
    </build>
</project>
```

子目录 `learning-parent/learning-service/pom.xml`：

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0">
    <modelVersion>4.0.0</modelVersion>
    <parent>
        <groupId>com.example.learning</groupId>
        <artifactId>learning-parent</artifactId>
        <version>1.0.0-SNAPSHOT</version>
        <relativePath>../pom.xml</relativePath>
    </parent>
    <artifactId>learning-service</artifactId>

    <dependencies>
        <dependency>
            <groupId>org.junit.jupiter</groupId>
            <artifactId>junit-jupiter</artifactId>
            <scope>test</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
            </plugin>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-surefire-plugin</artifactId>
            </plugin>
        </plugins>
    </build>
</project>
```

子模块继承 groupId、version、属性和管理配置；JUnit 必须自己声明才引入。父 POM 若把某个依赖直接写在 dependencies 中，子项目通常会继承并引入它，因此“统一版本”优先写 dependencyManagement。

此模板聚焦继承，实际团队工程还应统一其他参与构建的插件版本。

## 3. 哪些内容会继承

| 内容 | 常见行为 |
|---|---|
| groupId、version | 子项目省略时可从父项目继承 |
| artifactId | 子项目自己定义 |
| packaging | 子项目不继承父项目的 pom packaging，默认仍为 jar |
| properties | 继承；同名属性可在子项目重新定义 |
| dependencies | 可继承，可能让所有子模块都引入库 |
| dependencyManagement | 继承依赖默认版本和配置 |
| build/plugins | 可继承版本、配置和 executions，受 inherited 等控制 |
| build/pluginManagement | 继承插件默认管理信息 |
| modules | 聚合信息，不作为子项目的模块列表继承 |
| Profile | 不应理解成完整 Profile 定义直接继承；父 POM 已激活 Profile 的效果可进入子模型 |

插件、配置项与模型元素有各自合并规则，不能用“子 POM 整个替换父 POM”概括。

## 4. 覆盖与合并

### 4.1 同名属性

父项目定义 `<junit.version>5.11.4</junit.version>`，子项目可以重新定义同名属性。若父项目直接用该属性声明管理版本，子项目通常可通过覆盖属性改变最终值。

但如果版本来自**导入 BOM 内部的属性**，仅在消费者里声明同名属性通常不能重写 BOM 内部已经解析的版本。需要在当前 dependencyManagement 显式管理对应依赖，或使用该框架官方支持的父 POM/版本覆盖方式，并查看 effective-pom。

### 4.2 依赖按标识合并

继承中的依赖按 `groupId + artifactId + type + classifier` 等标识合并，不是每写一条就无限追加。子项目可以覆盖同一依赖的版本等信息。

不要在同一个 dependencies 列表里重复声明同一标识来“覆盖版本”；这可能产生模型警告，未来 Maven 版本也可能更严格。修改原声明或集中管理版本。

### 4.3 插件按坐标、执行按 ID 合并

同一插件通常按 groupId/artifactId 合并。父子 execution 的 ID 相同，会参与同一执行项合并；ID 不同，可能两个都保留，导致任务执行多次。

防止某个父插件向子项目继承，可在父 POM 的对应 plugin 或 execution 中配置：

```xml
<inherited>false</inherited>
```

插件 configuration 默认合并时，子项通常优先，但复杂集合不一定按期望整体替换。可以对适用节点使用：

```xml
<configuration combine.self="override">
    <release>21</release>
</configuration>
```

这段放在插件中，表示覆盖相应 configuration 合并。对适用的集合节点也可使用 `combine.children="append"` 追加；它可能导致列表重复，应先检查插件参数结构和有效 POM，再使用。

这些是插件配置合并提示，不是可以放在 POM 任意位置的通用 XML 操作符。

## 5. 父 POM 找不到或找错

`Non-resolvable parent POM` 常见原因：父坐标错误、父 POM 未发布、仓库缺失、认证失败或 relativePath 不正确。

默认会尝试 `../pom.xml`。如果那里不是声明坐标的父 POM，Maven 可能提示 `parent.relativePath points at wrong local POM`。先修正路径和坐标；父项目来自远程仓库且不应走本地相对路径时可用 `<relativePath/>`。

根聚合工程中能构建，不代表单独把子目录复制出去仍能解析父 POM。父项目也需要有可靠的分发方式。

## 6. 依赖版本冲突：一个具体例子

下面是教学依赖图，A/B/C/D 为抽象构件，不可直接下载：

```text
app
├── library-a:1.0
│   └── common:1.0
└── library-b:1.0
    └── helper:1.0
        └── common:2.0
```

若没有其他管理配置干预，common:1.0 路径更近，通常胜出。library-b 若调用 common:2.0 才有的方法，编译 app 可能成功，运行相关代码却出现 `NoSuchMethodError`。

同深度例子：

```text
app -> library-a -> common:1.0
app -> library-b -> common:2.0
```

通常先声明的路径胜出。调整声明顺序可能改变结果，但不应把它当作长期冲突治理策略；应明确选择并统一兼容版本。

## 7. 冲突处理的步骤

1. **定位来源**：查看全部依赖树，再按目标构件过滤。
2. **确认最终模型**：父 POM、BOM、Profile、直接声明中是否管理了版本。
3. **判断兼容性**：阅读库升级说明，确认所有调用方可使用目标版本。
4. **统一版本**：在适当父层的 dependencyManagement 管理；必要时直接声明项目确实使用的依赖。
5. **排除不需要的路径**：只有确认某依赖应被替代或完全不需要时才加 exclusion。
6. **验证运行**：复跑测试，并检查实际部署归档、容器类库和运行路径。

```bash
mvn dependency:tree -Dverbose
mvn dependency:tree '-Dincludes=com.example:common'
mvn help:effective-pom
```

第二条只是过滤示意，要替换为真实冲突坐标。verbose 中可能显示 `omitted for conflict`，表示节点未被选中，不是它从上游 POM 中消失了。

统一版本的示意片段，版本号须换为真实、验证过的版本：

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>com.example</groupId>
            <artifactId>common</artifactId>
            <version>2.0</version>
        </dependency>
    </dependencies>
</dependencyManagement>
```

如果 app 源码直接使用 common，还应在 dependencies 中声明它，可以省略已管理的 version。单纯管理版本不会把它引入。

当前项目直接显式声明的 version 可以覆盖相应管理默认值；父级继承的管理配置可在子级重新管理；当前 POM 对依赖的显式管理通常优先于导入 BOM 提供的条目。涉及多个 BOM 或父链时，以有效 POM 和实际依赖树为准，不要把规则简化为一条绝对优先级。

## 8. 用 Enforcer 提前暴露问题

在第 6 篇 Enforcer 的 rules 中可增加：

```xml
<dependencyConvergence/>
```

它要求依赖路径上的版本收敛，有助于在构建时发现不同路径版本不一致。也可按团队政策选择：

```xml
<requireUpperBoundDeps/>
```

二者目标不同：前者强调版本一致，后者检查解析出的版本不低于路径中声明的较高版本。高版本也可能不兼容，因此都不能代替兼容性测试。具体范围、排除和 SNAPSHOT 处理要看所用规则版本文档。

## 9. 同名类冲突不等于同坐标版本冲突

不同 GAV 也可能包含同一个完整类名，例如旧库与新库更换了 groupId，却携带相同包。Maven 可以同时保留二者，普通版本调解不能自动解决。

常见情形包括：重复打包的工具类、旧新驱动并存、多个日志实现、容器自带库与应用自带库重复。

排查方式：

- 用 `jar tf` 检查实际归档内容，必要时用团队认可的重复类检测插件。
- Java 21 可通过 `java -Xlog:class+load=info -jar ...` 观察类加载来源，日志可能很大。
- 检查容器 classloader 策略、启动脚本 classpath、可执行 JAR 的嵌套依赖。
- 明确移除应淘汰的库，统一日志实现；确有隔离需求时再评估 Shade relocation，并测试反射、SPI 和资源合并。

不要认为“dependency:tree 只显示一个版本”就意味着运行时一定没有重复类。

## 10. 插件依赖冲突与配置冲突

构建插件有自己的依赖空间，项目 dependencyManagement 不会自动管理所有插件依赖。若插件报错，应检查插件版本、插件自身 dependencies、Maven/JDK 兼容性；优先选择官方兼容版本，不要随意覆盖插件内部库。

配置冲突则常来自：父子插件合并、相同 execution ID、多个 Profile、命令行属性、IDE 另选 settings。处理时看 effective-pom、active-profiles 和启动参数，再修改配置来源。

最小排查组合是：`mvn -v`、`help:effective-pom`、`help:active-profiles`、`dependency:tree`，最后以实际运行时加载的类和测试结果确认。
