# 依赖管理与仓库

## 1. 声明依赖

把依赖放在 POM 的 `dependencies` 内：

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.11.4</version>
    <scope>test</scope>
</dependency>
```

Maven 获取的不只是 JAR，还会读取依赖的 POM，进而解析其传递依赖。JUnit 聚合依赖会带来测试 API、引擎等组件；依赖版本和测试插件版本需要一起考虑。

## 2. 直接依赖与传递依赖

```text
当前项目 A
└── 直接依赖 B
    └── B 依赖 C，C 可能成为 A 的传递依赖
```

是否传递还受 scope、optional、exclusions 等影响。自己源码直接使用的库应显式声明，不要长期依赖“另一个库碰巧带进来它”。

## 3. scope：依赖在哪些 classpath 可用

| scope | 主源码编译 | 测试编译/运行 | 主程序运行 | 常见用途 |
|---|---|---|---|---|
| `compile`（默认） | 是 | 是 | 是 | 业务使用的通用类库 |
| `provided` | 是 | 是 | 否，由外部提供 | 容器提供的 Servlet API |
| `runtime` | 否 | 是 | 是 | 通过 SPI 等加载的数据库驱动 |
| `test` | 否 | 是 | 否 | JUnit、测试辅助库 |
| `system` | 是 | 是 | 否，由外部安排 | 指定机器绝对路径的历史用法，应避免 |
| `import` | 不适用 | 不适用 | 不适用 | 仅用于 dependencyManagement 导入 POM/BOM |

此表描述 Maven 常规 classpath，不代表插件一定把依赖打进归档。普通 JAR 默认不包含任何依赖 JAR；WAR、Shade、Spring Boot 等有各自打包规则。

### scope 的传递简表

行是 A 对 B 的 scope，列是 B 对 C 的 scope；结果为 C 对 A 的传递 scope，`—` 表示不传递。

| A → B / B → C | compile | provided | runtime | test |
|---|---|---|---|---|
| compile | compile | — | runtime | — |
| provided | provided | — | provided | — |
| runtime | runtime | — | runtime | — |
| test | test | — | test | — |

例如 A 以 compile 依赖 B，而 B 的测试库是 test，这个测试库不会变成 A 的依赖。

## 4. 版本冲突如何选择

对常见依赖冲突，Maven 使用“路径最近优先”，相同深度通常按声明顺序优先。不是默认选择版本号最大的那个。

```text
A -> B -> D:1.0
A -> C -> E -> D:2.0
```

通常选择距离 A 更近的 `D:1.0`。项目的依赖管理可以影响传递依赖的最终版本；显式直接依赖的版本也应一起检查，不能只依赖最近原则判断。

```bash
mvn dependency:tree
mvn dependency:tree -Dverbose
mvn dependency:tree -Dincludes=org.junit.jupiter:*
```

在 zsh 等 shell 中，应给含通配符的参数加引号，所以上一条命令实际建议写成：

```bash
mvn dependency:tree '-Dincludes=org.junit.jupiter:*'
```

解决冲突时先确认兼容版本，再用直接声明或 dependencyManagement 统一。构建成功并不证明运行时二进制兼容，仍需要测试。

## 5. dependencyManagement 与 BOM

dependencyManagement 管理版本等默认信息，**不会自动引入库**。

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.junit</groupId>
            <artifactId>junit-bom</artifactId>
            <version>5.11.4</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>
```

BOM（Bill of Materials）是一份用 POM 管理一组依赖版本的清单。上面的 JUnit 版本由 BOM 管理，项目仍要在 dependencies 中声明实际使用的库。

导入 BOM 不等于继承父 POM，也不会导入对方的全部插件和构建配置。多个 BOM 管理同一依赖时要检查最终生效版本；不要假定最后导入的一定覆盖前面。

项目的 dependencyManagement 主要管理项目依赖，不会自动统一构建插件内部的依赖。

## 6. exclusions 与 optional

排除某条依赖路径上的传递依赖：

```xml
<dependency>
    <groupId>com.example</groupId>
    <artifactId>some-library</artifactId>
    <version>1.0.0</version>
    <exclusions>
        <exclusion>
            <groupId>com.example</groupId>
            <artifactId>unwanted-library</artifactId>
        </exclusion>
    </exclusions>
</dependency>
```

这里的 `com.example` 构件是结构示意，不能直接当作可下载的真实依赖。排除只作用于指定路径；另一路径仍可能引入同一库。

库作者在某个 dependency 中设置 `<optional>true</optional>`，表示该依赖通常不自动传递给下游消费者。它仍然是当前库自身的依赖。消费者需要相关功能时自行声明，不是 Maven 在运行时自动选择加载。

## 7. 三类仓库

| 仓库 | 用途 |
|---|---|
| 本地仓库 | 默认 `~/.m2/repository`，存放下载缓存和 `install` 的本地产物 |
| Maven Central | 公共远程仓库，Maven 默认模型中已配置 |
| 私服或其他远程仓库 | 托管公司内部库、代理公共仓库、保存发布产物 |

依赖解析会使用本地已有内容，并按仓库配置、版本类型和更新策略决定是否访问远程。不能简单理解成每次构建都从网上重新下载。

普通项目通常不需要重新声明 Central。仓库应尽量少且来源可信，不要遇到下载慢就随意增加多个陌生仓库。

## 8. mirror、repository 与发布目标

- `repositories`：告诉 Maven 可从哪里获取依赖。
- `pluginRepositories`：插件解析的仓库配置。
- `mirrors`：在 settings.xml 中，把匹配的仓库访问路由到指定地址。
- `distributionManagement`：定义 `deploy` 要上传到哪里。

公司统一私服的 settings.xml 片段示意：

```xml
<mirrors>
    <mirror>
        <id>company-mirror</id>
        <mirrorOf>*</mirrorOf>
        <url>https://repo.example.com/repository/maven-public/</url>
    </mirror>
</mirrors>
<servers>
    <server>
        <id>company-mirror</id>
        <username>${env.MAVEN_REPO_USER}</username>
        <password>${env.MAVEN_REPO_PASSWORD}</password>
    </server>
</servers>
```

这是放入 `settings` 内的片段，地址需替换为实际私服。环境变量由本机或 CI 的秘密管理注入；不要把真实凭据写进 POM 或日志。

`mirrorOf=*` 会匹配所有仓库，要求私服能提供项目所需内容。若要排除某仓库可使用 `*,!internal-releases` 等表达式，具体按团队策略配置。镜像不是“多个地址轮流试”的负载均衡列表。

发布目标配置在 POM 的 `distributionManagement` 中；它的仓库 ID 应匹配上传认证使用的 server ID。下载镜像的 ID 和发布目标的 ID 不必相同。不要把 deploy 的发布目标误写成普通的聚合下载仓库。

## 9. SNAPSHOT 与 Release

| 类型 | 示例 | 语义 |
|---|---|---|
| SNAPSHOT | `1.0.0-SNAPSHOT` | 开发中，可更新 |
| Release | `1.0.0` | 发布后应保持内容不可变 |

远程 SNAPSHOT 通常通过元数据解析到带时间戳和构建号的实际文件；同一个 `-SNAPSHOT` 坐标可能在不同时间得到不同内容。Release 的不可变性应由仓库策略保证，不是文件名自动保证。

```bash
mvn -U verify
```

`-U` 强制检查更新的快照和缺失的 release；它不是无条件重新下载所有已经存在的 release。避免用版本范围、`LATEST`、`RELEASE` 作为常规团队版本策略。

## 10. 本地 JAR 与离线构建

没有远程仓库的第三方 JAR 可临时安装到本地：

```bash
mvn install:install-file -Dfile=/path/to/vendor-sdk.jar -DgroupId=com.vendor -DartifactId=vendor-sdk -Dversion=1.0.0 -Dpackaging=jar
```

如果供应商提供正式 POM，应通过 `-DpomFile=/path/to/pom.xml` 使用它，保留依赖信息。长期方案是按许可证和团队规则发布到私服；只安装在自己电脑上会造成 CI 和同事构建失败。避免 `systemPath` 和直接提交大量 JAR。

```bash
mvn dependency:go-offline
mvn -o verify
```

`go-offline` 可以预取很多依赖和插件，但不同 Profile、插件运行期下载、工具链等仍可能需要额外内容。真正的离线可用性应在断网或隔离环境中执行目标构建验证。
